# Авито.Кухня — MVP

Тестовое задание, backend-стажёр, осенняя волна 2026.

## Описание проекта

Авито.Кухня — сервис доставки еды, расширяющий основную площадку Авито.
В рамках MVP реализованы два API:

- **клиентское API** — веб-клиент смотрит список заведений, их меню и
  оформляет заказ, отслеживает его статус;
- **API заведений** — заведение (из закрытого списка) ведёт своё меню и
  получает/обрабатывает заказы.

Авторизация и аутентификация сознательно не реализованы — это явно вынесено
за скобки в условии задания. `user_id` передаётся клиентом явно.

Для демонстрации интеграции в этом же репозитории реализован
**restaurant-service** — отдельный сервис на Go, имитирующий работающее
заведение: он принимает вебхук о новом заказе и продвигает его статус
(`accepted -> cooking -> ready`), вызывая обратно API площадки.

## Архитектура

См. `docs/c4-container.puml` (C4, Level 2 — Container). Кратко:

```
Пользователь -> Веб-клиент (вне MVP) -> API-сервис (Go) -> PostgreSQL
                                              |   ^
                                   webhook: новый заказ
                                              |   |
                                              v   | обновление статуса
                                     restaurant-service (Go, пример заведения)
```

Оба сервиса — независимые Go-модули (`/` и `/restaurant-service`) в одном
репозитории, поднимаются вместе через `docker-compose.yml`.

### Почему так

- **API-сервис не хранит состояние заказа "на стороне заведения"** —
  заведение является внешней системой, с которой площадка общается только
  через HTTP (webhook туда, callback обратно). Это ближе к реальной
  интеграции, чем общая БД на двоих.
- **Переходы статуса заказа валидируются доменным правилом**
  (`internal/domain/models.go`, `CanTransition`) — заведение не может
  перевести заказ, например, из `created` сразу в `delivered`.
- **Заведение работает только со своими данными.** Все ручки API
  заведений имеют вид `/api/v1/restaurant/{restaurant_id}/...`; заказ или
  позиция меню чужого заведения для него "не существуют" (404). Пока нет
  аутентификации, `restaurant_id` берётся из пути — в проде он бы брался
  из токена/mTLS-сертификата заведения, а ручки остались бы теми же.
- **Пользователь может отменить свой заказ**, пока заведение не начало
  готовить (`created`/`accepted`); дальше отмена — только со стороны
  заведения.
- **Роутинг — на стандартном `net/http` (Go 1.22+)**, без сторонних
  роутеров: `mux.HandleFunc("POST /api/v1/orders", ...)` достаточно для
  MVP и не тянет лишних зависимостей.

## Структура репозитория

```
cmd/api/main.go            — точка входа API-сервиса площадки
internal/domain            — доменные модели и бизнес-правила (статусы заказа)
internal/repository        — доступ к PostgreSQL (pgx)
internal/service           — бизнес-логика сценариев (каталог, заказы)
internal/handler           — HTTP-хендлеры
internal/httpclient        — вебхук-клиент "площадка -> заведение"
internal/httpserver        — middleware, healthcheck
migrations/                — SQL-миграции (up/down) + сид демо-заведения
api/openapi.yaml           — OpenAPI-спецификация
docs/                      — CJM (пользователь, заведение), C4-диаграмма
restaurant-service/        — отдельный Go-модуль: пример заведения
```

## Основные сценарии (CJM)

- `docs/cjm-user.puml` — пользователь: список заведений → меню → корзина →
  заказ → отслеживание статуса, включая ветку "товара нет в наличии" и
  ветку отказа/отмены заказа.
- `docs/cjm-restaurant.puml` — заведение: ведение меню → получение заказа
  вебхуком → приготовление по шагам → либо отказ, если товар внезапно
  закончился.

Диаграммы в формате PlantUML, рендерятся любым PlantUML-совместимым
инструментом (plugin в IDE, plantuml.com/plantuml, `plantuml *.puml`).

## Схема БД

4 таблицы (полные DDL — в `migrations/000001_init.up.sql`):

- **restaurants** — заведения из закрытого списка; `callback_url` — адрес,
  на который площадка шлёт вебхук о новом заказе.
- **menu_items** — позиции меню, привязаны к заведению; `is_available`
  отвечает за сценарий "товара нет в наличии".
- **orders** — заказ пользователя; `status` ограничен CHECK-constraint'ом
  до конечного набора значений жизненного цикла.
- **order_items** — состав заказа; цена фиксируется на момент заказа
  (`price_cents_at_order`), чтобы последующее изменение цены в меню не
  меняло уже оформленные заказы.

Внешние ключи: `menu_items.restaurant_id -> restaurants.id`,
`orders.restaurant_id -> restaurants.id`, `order_items.order_id -> orders.id`
(с `ON DELETE CASCADE`), `order_items.menu_item_id -> menu_items.id`.
Денежные суммы хранятся в минимальных единицах валюты (`*_cents`), чтобы
избежать проблем с плавающей точкой.

## Как запустить

```bash
docker compose up --build
```

Поднимутся: `postgres`, одноразовый `migrate` (накатывает миграции и сид
с одним демо-заведением и тремя позициями меню), `api` (:8080),
`restaurant-service` (:9090).

Проверка сценария целиком:

```bash
# список заведений
curl localhost:8080/api/v1/restaurants

# меню (позиция id=3 "Морс" специально помечена недоступной)
curl localhost:8080/api/v1/restaurants/1/menu

# оформить заказ
curl -X POST localhost:8080/api/v1/orders \
  -H 'Content-Type: application/json' \
  -d '{"user_id":1,"restaurant_id":1,"items":[{"menu_item_id":1,"quantity":2}]}'

# посмотреть, как статус меняется во времени (created -> accepted -> cooking -> ready)
curl localhost:8080/api/v1/orders/1

# отменить свой заказ (успеет, только пока он created/accepted)
curl -X POST localhost:8080/api/v1/orders/1/cancel \
  -H 'Content-Type: application/json' -d '{"user_id":1}'

# API заведения: добавить позицию и снять/вернуть товар в наличие
curl -X POST localhost:8080/api/v1/restaurant/1/menu-items \
  -H 'Content-Type: application/json' -d '{"name":"Чай","price_cents":5000}'
curl -X PATCH localhost:8080/api/v1/restaurant/1/menu-items/3/availability \
  -H 'Content-Type: application/json' -d '{"is_available":true}'
```

## Известные упрощения MVP

Осознанно не делали ради скорости, в проде поступили бы иначе:

- **Уведомление заведения — синхронный HTTP-вызов без ретраев и
  идемпотентности.** В проде — outbox-таблица + очередь (Kafka/SQS) с
  ретраями и dedup по `order_id`, чтобы не терять заказ при недоступности
  заведения и не задваивать его при ретрае.
- **Нет аутентификации/авторизации** — по условию задания. `user_id` и
  `restaurant_id` передаются явно; проверки "свой/чужой" при этом уже есть.
- **`restaurant-service` принимает вебхук идемпотентно** (повтор того же
  `order_id` игнорируется), но сама площадка вебхук не ретраит — см. пункт
  выше про outbox.
- **`restaurant-service` хранит заказы в памяти**, а не в своей БД — это
  просто демонстрационная заглушка реального сервиса заведения.
- **Нет пагинации** в списках заведений/заказов — на объёме MVP не нужна,
  при росте — обязателен `cursor`/`limit`.
- **Нет outbox/событийной шины между сервисами площадки** — при
  масштабировании (например, добавлении сервиса доставки/курьеров)
  обновления статуса заказа стоит публиковать событием, а не только
  синхронным PATCH.
- **Один экземпляр `restaurant-service` на все заведения из ТЗ** — в
  реальности у каждого заведения свой независимый сервис со своим
  `callback_url`; схема БД и API это уже поддерживают (`callback_url` —
  поле на заведение), демо ограничено одним для простоты docker-compose.

## Промпт / план, по которому писался код

Итеративно, слой за слоем в рамках одного Go-модуля:

1. Домен: модели `Restaurant`, `MenuItem`, `Order`, `OrderItem` + правило
   допустимых переходов статуса заказа (`CanTransition`).
2. Репозитории на `pgx/v5` (`pgxpool`), заказ создаётся вместе с позициями
   одной транзакцией.
3. Сервисный слой: `CatalogService` (заведения/меню) и `OrderService`
   (создание заказа с проверками наличия и активности заведения, смена
   статуса с проверкой перехода, асинхронный вебхук в заведение).
4. HTTP-хендлеры на стандартном `net/http` (Go 1.22 method+path routing),
   единый маппинг доменных ошибок в HTTP-статусы.
5. Второй Go-модуль `restaurant-service`: принимает вебхук, симулирует
   готовку тремя шагами с обратными вызовами в API площадки.
6. Миграции, `docker-compose.yml`, `Dockerfile` для обоих сервисов.
7. OpenAPI-спецификация вручную по уже реализованным хендлерам.
8. CJM (пользователь, заведение) и C4-диаграмма — как итоговая
  документация принятых решений.
